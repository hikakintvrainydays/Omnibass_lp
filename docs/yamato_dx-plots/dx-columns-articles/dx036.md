# 小規模システム開発の費用感と発注時のチェックリスト

中小企業がDXを進める際、SaaSやノーコードだけでは要件を満たせず、外部のシステム開発会社に小規模システム開発を発注するケースが出てきます。一方で、「見積もりが妥当か分からない」「そもそも何を頼めばよいか整理できていない」という声もよく聞かれます。本稿では中小機構や経済産業省のDX支援関連資料を参照しつつ、小規模システム開発の費用感を考えるための前提と、発注前に押さえたいチェックリストを整理します。本稿は具体的な金額相場を保証するものではなく、見積もりを読み解くための観点を整理する目的で書かれています。

## 小規模システム開発とは

ここで言う「小規模システム開発」は、おおむね次のような範囲を指します。

- 既存業務の一部をWebアプリ・モバイルアプリで効率化する
- パッケージ・SaaSでは要件を満たせない部分を独自開発する
- 既存システムと外部サービスをAPIで連携する追加開発
- 受発注・予約・問い合わせなど、特定業務に特化したシステム

数人月〜十数人月程度のプロジェクトを想定したスケールです。基幹システムの全面刷新や、大規模なERP導入はここでは扱いません。

## 中小企業のDX文脈における小規模開発の位置づけ

経済産業省「中堅・中小企業向けDX推進の手引き2025」や中小機構のDX支援関連ページでは、中小企業のDXは「身の丈に合った形で段階的に進める」ことが推奨されており、SaaS+ノーコード+小規模開発を組み合わせる形が現実的だと整理されています。すべてを内製するのも、すべてを大規模パッケージで埋めるのも難しいため、「足りない部分を小規模開発で補う」アプローチが取られやすい背景があります。

## 費用相場の考え方

小規模システム開発の費用は、地域・会社規模・開発体制・技術要件・契約形態によって大きく変わるため、「相場」を一律に語ることは難しい領域です。代わりに、見積もりを読むときの基本的な考え方として、次の観点を押さえることが重要です。

- 工数(人月・人日)ベースでの算出が一般的
- 単価は職種(PM、設計者、開発者、デザイナー)と発注先(大手SIer / 中堅 / フリーランス)で大きく異なる
- 要件定義・設計・実装・テスト・保守の各工程で、工数の比重が変わる
- インフラ(クラウド料金)・SaaSライセンス・ドメインなどの実費が別途必要
- 仕様変更が起こりやすいため、契約形態(請負/準委任)によって追加費用の発生有無が変わる

「見積もり総額」よりも「内訳と前提条件」を確認できるかどうかが、相場感を判断するうえで重要です。

## 見積もりの読み方

複数社から見積もりを取った場合、金額だけを比較すると判断を誤りがちです。次の観点で読み解く必要があります。

- スコープ: どこまでの機能を含むのか(管理画面、メール通知、レポートなど抜けがないか)
- 工程: 要件定義・設計・実装・テスト・リリース・保守が含まれているか
- 体制: PM・開発者・デザイナーの構成と単価の前提
- 納品物: 仕様書、設計書、ソースコード、運用手順書、テスト結果など
- 著作権・ソースコードの扱い
- 保守・運用費の月額(リリース後)
- インフラ費用とランニングコストの扱い
- 仕様変更・追加要望時の対応方針

同じ100万円の見積もりでも、「PM工数がほぼ含まれない」「保守費が別途毎月かかる」「ソースコードが渡されない」など条件が違えば、実質的なコストは大きく変わります。

## 発注前チェックリスト

発注前に整理しておきたい項目を一覧にすると次の通りです。

### 業務・要件まわり

- 解決したい業務課題が一文で言語化できているか
- 関係する部署・担当者・役割が整理されているか
- 既存システム・SaaSとの連携範囲が明確か
- 利用人数・データ量・アクセス頻度の見積もりがあるか
- セキュリティ・個人情報の取り扱い方針が決まっているか

### システム・技術まわり

- パッケージ・SaaS・ノーコードで代替できないかを検討したか
- インフラ(クラウド/オンプレ)の方針が決まっているか
- 既存システムとの連携可否(API・CSV・他)が確認されているか
- スマホ対応・ブラウザ対応の前提が明確か
- バックアップ・障害時対応の要件が整理されているか

### 契約・体制まわり

- 発注先の実績・体制(役割と人数)が確認できているか
- 請負か準委任か、契約形態の意味を理解しているか
- 仕様変更時の対応ルールが取り決められているか
- 検収条件・受け入れテストの基準があるか
- 著作権・ソースコードの帰属が明文化されているか
- リリース後の保守体制と費用感が決まっているか

### 社内まわり

- プロジェクトの社内責任者(意思決定できる人)が決まっているか
- 現場担当者がレビュー・テストに割ける時間が確保されているか
- 経営層・現場の合意形成が取れているか
- 補助金(IT導入補助金など)の活用可否を検討したか

これらを最低限埋めてから発注に進むことで、後々のトラブルを大きく減らせます。

## よくあるトラブルと防止策

小規模システム開発でよく起こるトラブルと、その防止策を整理します。

- 「思っていたものと違う」: 要件定義段階でモック・画面遷移図を作り、合意してから実装に進む
- 「途中で要件が膨らみ、追加費用が発生」: 契約時に追加要件のルールを明文化し、変更管理表で管理する
- 「リリース後に運用できない」: 運用手順書・障害対応の連絡ルートを納品物に含める
- 「ソースコードがブラックボックス」: 著作権の帰属とソースコード開示を契約に盛り込む
- 「保守料金が予想外に高い」: 月額保守の対象範囲(障害対応のみ / 軽微改修込み等)を事前に決める
- 「補助金との整合が取れない」: 補助金活用を検討する場合、対象経費・対象期間を発注前に確認する

これらは知識さえあれば防げるものが多く、発注前に1〜2時間かけて整理するだけで、トラブルの確率を大きく下げられます。

## 「相見積もり3社」と「最初に話せるパートナー」のバランス

小規模開発では、3社程度から相見積もりを取るのは健全ですが、それ以上に重要なのは「自社の業務をよく理解してくれるパートナーがいるか」です。要件定義の前段から相談できる相手がいると、無理な仕様で発注して失敗するリスクが減ります。発注先選定は、価格だけでなく「自社の業務に踏み込んだ提案ができるか」「リリース後の運用まで一緒に考えてくれるか」という観点で見るのが、長く使えるシステムを作る近道です。
